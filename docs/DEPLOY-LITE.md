# Установка на VPS с 1 ГБ RAM, по IP и без домена

Подготовлен отдельный путь установки: SQLite, один процесс Gunicorn с двумя потоками, отдельный сборщик, nginx, systemd и HTTPS-сертификат для публичного IP. Docker/PostgreSQL не устанавливаются. Если swap отсутствует и достаточно места, добавляется 1 ГБ swap.

**Статус:** установщик подготовлен и локально проверен частично. На целевом VPS он ещё не выполнялся. Облачная среда разработки не предоставила SSH-транспорт к публичному адресу; это не проверка доступности самого VPS. Не считать наличие этих файлов подтверждением работающего сайта.

## Что нужно

- Ubuntu 24.04+ или Debian 12+ с Python 3.11+, systemd, root SSH и публичным IPv4.
- На VPS свободны порты 80, 443 и 8000. В панели провайдера должны разрешаться входящие 22/TCP (либо ваш SSH-порт), 80/TCP и 443/TCP. Порт 8000 наружу не открывается.
- На Windows 10 установлен Python 3.12 (он уже нужен для локальной CRM) и стандартный Windows OpenSSH Client (`ssh.exe` и `scp.exe`). Git, Docker, PuTTY и отдельная конвертация ключа не нужны для незашифрованного RSA PPK v2.

## Запуск на Windows

1. Скачайте/распакуйте актуальную версию проекта. Откройте **`deploy-server-windows.bat`** в корне папки.
2. Введите публичный IP сервера. В окне выбора укажите свой SSH-ключ, например `1.ppk`.
3. Дождитесь установки. Затем создайте владельца CRM в появившемся диалоге. При переносе прежней базы желательно использовать то же имя владельца. Символы пароля не отображаются.
4. Откройте показанный адрес `https://ВАШ_IP`. Войдите и через «Резервные копии» восстановите ZIP, который предварительно скачали из CRM на ноутбуке.

Для нестандартного SSH-порта или запуска без выбора файла:

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\deploy\deploy-from-windows.ps1 -ServerIp 94.141.98.18 -Port 22 -KeyPath "C:\путь\к\1.ppk"
```

`ExecutionPolicy` задаётся только для процесса запуска установщика, не меняет постоянную политику компьютера. В корпоративной Windows групповая политика может запрещать такой запуск. OpenSSH-клиент при необходимости включается в «Параметры → Приложения → Дополнительные компоненты → Клиент OpenSSH».

SSH использует проверку ключа хоста (`accept-new`): первое подключение запоминает ключ, изменение ранее известного ключа блокируется. Проверяйте IP перед запуском; при предупреждении о смене ключа не удаляйте known_hosts вслепую.

## Что делает установщик

- Локально проверяет целостность PPK и преобразует его в SSH-формат. Временная папка ограничена вашим аккаунтом Windows, после завершения удаляется. Ключ на VPS не передаётся и не попадает в код проекта.
- Передаёт архив приложения по SCP без штатных `.env`, локального ключа CRM, SSH-ключей, БД, резервных копий, Git и виртуального окружения. GitHub-токены серверу не нужны.
- Проверяет поддерживаемую ОС, свободные порты и посторонние nginx-сайты; при конфликте останавливается.
- Создаёт непривилегированного пользователя `egrcrm`, ставит приложение в новый каталог `/opt/egrcrm/releases/…`, хранит БД/копии отдельно в `/var/lib/egrcrm`.
- Создаёт серверный секрет один раз в `/etc/egrcrm/egrcrm.env` с правами 0600. Значение не выводится. Приложение работает с `DEBUG=0` и защищёнными cookies.
- При повторном запуске останавливает только собственные службы и делает SQLite-копию до миграций. Не удаляет старые данные и релизы.
- Выпускает публичный HTTPS-сертификат для IP через Certbot 5.9 и ACME-профиль `shortlived`. Для выпуска создаётся ACME-аккаунт без email с принятием условий Let's Encrypt. До успешного выпуска HTTP обслуживает только challenge и страницу 503, не форму входа CRM.
- Настраивает проверку продления сертификата каждые 6 часов, автозапуск сайта и сборщика после перезагрузки. Не меняет SSH-настройки и не включает UFW, если он был выключен; у активного UFW добавляет 80/443.
- Проверяет локальный HTTPS с реальной валидацией сертификата, затем предлагает создать владельца. Обход TLS/самоподписанный публичный сертификат не используется.

Старая база с ноутбука **не передаётся автоматически**: её следует перенести через версионный ZIP после установки. Восстановление заменяет данные сервера по стандартным правилам CRM и ставит источник на паузу. Не включайте массовый сбор до проверки одного УНП и одного завершённого дня на новом IP.

## Если установка остановилась

Если видите 502 или `Services were installed but the HTTPS health check failed`, откройте **`diagnose-server-windows.bat`** из обновлённой папки проекта. Введите тот же IP и выберите тот же ключ. Это отдельный режим: он не устанавливает пакеты, не меняет настройки, не перезапускает службы и не изменяет базу. Рядом появится файл `server-diagnostic-ДАТА.txt` с фактическими ошибками служб, доступом к файлам и импортом приложения; передайте его для разбора. Секретный `.env` и SSH-ключ в отчёт не включаются. Если есть браузерная консоль VPS, достаточно начать с `journalctl -u egrcrm-web -n 60 --no-pager`.

Сохраните текст ошибки. Установщик не объявляет успех, если выпуск сертификата или проверка сайта не прошли. Частые причины: другая ОС, закрытый порт 80, отсутствие OpenSSH на Windows, неверный ключ/SSH-порт, занятые порты. На сервере могут остаться подготовленные каталоги и пакеты; старая база и копия перед обновлением сохраняются.

Проверить на VPS:

```sh
systemctl status egrcrm-web egrcrm-worker
journalctl -u egrcrm-web -n 60
journalctl -u egrcrm-worker -n 60
systemctl list-timers egrcrm-cert-renew.timer
```

Ручная команда управления от root:

```sh
/usr/local/sbin/egrcrm-manage createsuperuser
/usr/local/sbin/egrcrm-manage backup_crm
```

Скачивайте ZIP-копии за пределы VPS. Копия на том же SSD не защищает от потери сервера. Старые каталоги релизов намеренно не удаляются автоматически; периодически проверяйте свободное место.

## Что проверено в разработке

- Bash-синтаксис установщика: успешно.
- Четыре теста упаковки/конвертации: целостность PPK, правильный DER, отказ от повреждённого/зашифрованного PPK, исключение БД/ключей/секретов/кэшей и отказ от симлинков источника.
- Предоставленный PPK v2 проверен и преобразован локально без вывода содержимого; RSA-параметры совпали с независимой конвертацией через cryptography, OpenSSH принимает полученный формат. Это не проверка авторизации ключа на VPS.
- Собран исходный архив и проверен состав: приватных ключей, БД и штатных секретов нет.
- В официальном пакете Certbot 5.9.0 проверены аргументы `--ip-address` и `--preferred-profile`, требование Python >=3.10. Установщик требует Python >=3.11 для приложения.

PowerShell в Windows, apt/systemd/nginx на реальном VPS, выпуск IP-сертификата, расход RAM и доступ к ЕГР на этом сервере пока **не проверены**. Их подтвердит успешный запуск и диагностика на целевом сервере. Из-за ограничения SSH этой облачной среды deployment не был выполнен агентом.

### Проверка после первого запуска на VPS

По присланному журналу подтверждены: Ubuntu 26.04, Python 3.14.4, доступ по SSH с Windows, установка зависимостей и миграций, получение публичного IP-сертификата и загрузка nginx. Проверка `/login/` возвращает 502; точная ошибка службы в исходном журнале отсутствует. Добавлен отдельный режим диагностики и автоматическая печать журнала при будущих сбоях установки. В локальном временном окружении Python 3.14.8 с теми же версиями Gunicorn/Django и одним worker с двумя потоками `/login/` вернул 200. Это не проверка службы на самом VPS и не подтверждение устранения 502.
