# Серверное размещение

Для небольшого VPS с 1 ГБ RAM и доступом без домена предусмотрен [отдельный установщик SQLite/systemd/HTTPS по IP](DEPLOY-LITE.md). Описанный ниже Compose-вариант использует PostgreSQL и два процесса сайта; для него разумнее больше RAM.

Подготовлены Docker Compose, PostgreSQL 16, Gunicorn, WhiteNoise, отдельный worker с автоперезапуском, постоянные Docker volumes. Это не факт размещения на купленном сервере: домен, HTTPS, доступ к ЕГР и независимое ежедневное расписание надо проверить на выбранном хосте.

1. Сервер с Docker/Compose и HTTPS reverse proxy. До длительной оплаты проверить ограниченный пилот ЕГР с этого сервера: УНП 193787017, контакты, один завершённый день. Не отключать TLS и не обходить 401/403/429.
2. В корне репозитория выполнить `python deploy/configure.py`, ввести домен. Создаётся приватный `.env` с новыми случайными ключами без вывода значений. Файл не коммитить и не отправлять в чат.
3. Настроить reverse proxy по `deploy/Caddyfile.example` с вашим доменом. Web публикуется только на 127.0.0.1:8000. Внешний клиент не должен обращаться к Gunicorn напрямую. `X-Forwarded-Proto` выставляет доверенный reverse proxy, не клиент.
4. `docker compose up -d --build`. Web применяет миграции, worker запускается после готовности web; PostgreSQL и архивы сохраняются в отдельных volumes. **Не выполнять `docker compose down -v` при обновлении**: `-v` удаляет данные.
5. `docker compose exec web python manage.py createsuperuser` — создать владельца. Проверить прямые URL без входа и аккаунт менеджера. Проверка HTTPS: `docker compose exec web python manage.py check --deploy`.
6. Создать и скачать резервную копию через UI, восстановить её в отдельной проверочной установке. Настроить `CRM_BACKUP_COPY_DIR` на смонтированный внешний путь или организовать защищённый перенос PostgreSQL-дампов администратором.
7. Включить расписание. Закрыть браузер, дождаться запуска и проверить новые строки в постоянной базе. Сохранить результат проверки, время и ошибки — ручной запуск не доказывает работу расписания.

## Обновление сервера

До замены файлов: `docker compose exec -T web python manage.py backup_crm` и скачать/скопировать архив за пределы сервера. Затем обновить код и `docker compose up -d --build`. Volumes сохраняются. `deploy/update.sh` делает архив уже работающего приложения перед сборкой. При ошибке миграции не удалять volumes и не пытаться открыть новую схему старым кодом: сохранить файлы и использовать проверенный архив/дамп.

## Поиск сайта

Поддержан ручной Brave Search: задайте `BRAVE_API_KEY` в защищённом окружении web и worker, разрешите HTTPS к `api.search.brave.com`. Наличие ключа не доказывает действительность тарифа или доступ. Поиск может оплачиваться; каждый запуск требует подтверждения пользователя. В приложение поступают кандидаты с URL/выдержкой и отметкой совпадения УНП, решение подтверждается человеком. Произвольные страницы не загружаются, внутренние URL отклоняются. Без ключа — «Не настроено»; при ошибке — ошибка, не «сайта нет».

## Проверка пакетных методов

`python manage.py verify_egr_period 2026-11-01 2026-11-03` сравнивает наборы УНП дневного и периодного методов на 1–7 днях. Команда сохраняет исходные ответы, соблюдает очередь/паузу и завершится ошибкой при расхождении. Массовая оптимизация автоматически не включается: сначала проверка эквивалентности реальных ответов.

## Проверки в среде разработки

Серверный образ собран с проверкой TLS. Тесты запускаются и на SQLite, и на временном PostgreSQL; отдельный PostgreSQL-тест проверяет параллельный импорт и ручную правку. Это не нагрузочный тест и не проверка доступности API с будущего production-сервера.

`check --deploy` по умолчанию может оставить W005/W021: HSTS для всех поддоменов и включение в preload намеренно не включены автоматически. Задавать SECURE_HSTS_INCLUDE_SUBDOMAINS=1 и SECURE_HSTS_PRELOAD=1 можно только после подтверждения HTTPS для соответствующих поддоменов и решения владельца домена. Это не причина отключать TLS, secure cookies или перенаправление на HTTPS.
